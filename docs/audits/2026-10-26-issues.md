Ready-to-file issue bodies for the actionable findings of `2026-10-26-system-audit.md`. One issue = one topic. Every body separates **observation** (what was reproduced/read) from **inference** (hypothesis), per the tracker conventions in `docs/agents/issue-tracker.md`; acceptance criteria are red-first — they name the minimal check that fails on the current tree and the expected verbatim shape after the fix.

## Critical

### ISSUE-1 — wallet: settlement costs ~23 sequential round-trips per Fill; batch it
Labels: ready-for-agent · Confidence: certain (statement count measured; timing estimated)
Evidence: `internal/wallet/ledger.go:67-108` (`Post` = journal INSERT + open-at-zero INSERT + balance UPDATE), `internal/wallet/settlement.go:47-84`, `internal/wallet/holds.go:63-86` (settleHold = UPDATE + guard SELECT). One transaction per poll of up to 500 records (`consumer.go:25,58-71`).
Impact: settlement ceiling on the order of 100–200 Fills/s; batch tx duration blocks the consumer.
Fix: collapse settleHold to one `UPDATE ... RETURNING`; pipeline the per-Fill statements with `pgx.Batch` (vendored; no new dependency); same transaction semantics.
Acceptance: a benchmark-style IT that settles a 500-Fill batch (fixture per the review-checklist funding rule: every Fill backed by a real hold) and asserts the server-side statement count per Fill drops below 8 — red on main (23), green after.

### ISSUE-2 — exchange: engine persistence serializes ~4 statements per Fill; use pgx.Batch
Labels: ready-for-agent · Confidence: certain (measured)
Evidence: `internal/exchange/apply.go:36-48` (per Fill: insertFill + 2 accrual UPDATEs + outbox INSERT), `internal/exchange/engine.go:207-218` (per-command single-row inbox INSERT loop), `consumer.go:25` (`PollRecords(ctx, 500)`).
Impact: ~1,500–2,500 round-trips per 500-record batch in one tx — roughly 10x below ADR-0010's throughput model.
Fix: multi-row inbox INSERT; merge the two accrual UPDATEs; batch outbox INSERTs; `pgx.Batch` flushes. No schema change.
Acceptance: an IT asserting the engine batch tx persists a 50-placement/50-fill mix in a bounded statement count (e.g. <= 15 statements for the whole batch) — red on main, green after.

### ISSUE-3 — exchange: MaxOpen cap runs a count(*) per placement inside the global lock, and silently skips on query error
Labels: ready-for-agent · Confidence: certain
Evidence: `internal/exchange/engine.go:59-61` (e.mu held across the batch tx), `:164-171` (`err == nil && open >= cap` — a DB error leaves the cap unenforced; every other failure in the path aborts).
Impact: per-placement round-trip under the engine-wide mutex; correctness hole (cap not enforced on a transient DB error); only submission rule with no test.
Fix: maintain the per-Member open-order count in memory (maintained on place/complete/cancel, recounted at Recover); return an error on count-lookup failure during the transition.
Acceptance: (a) unit test placing orders with a failing count query asserts rejection (red on main: placement succeeds); (b) `validatePlace` performs zero SQL round-trips — asserted by a test that runs it against a stub tx that fails on any Exec.

## High — engine and eventing

### ISSUE-4 — market/exchange: a fully-consumed Book side can never clear the published Depth (phantom liquidity)
Labels: ready-for-agent · Confidence: certain (five-hop chain verified)
Evidence: `internal/engine/engine.go:542-563` (empty side → `Items: nil`), `internal/events/orders.go:75-76` (`omitempty` drops len-0 sides from the wire), `internal/market/projection.go:209-229` (nil side = keep last-known), relayed as-is on `depth.{market}` (`internal/api/hub.go:213-220`). The market suite documents the gap: `internal/market/consumer_it_test.go:602-607`.
Impact: stale Depth served indefinitely on REST and WS after a sweep/cancel empties a side; breaks ADR-0011's full-snapshot resync promise.
Fix: drop `omitempty` (or add an explicit cleared-side marker); the projector already treats present-but-empty as clear (its own test proves the semantics).
Acceptance: a projection IT that empties one side and asserts `depth_levels` contains zero rows for it — red on main, green after. `TestDepthServesLastKnownPlateAcrossExchangeRestart` extended to assert cold-start emptying.

### ISSUE-5 — outbox: per-key publish ordering is claimed but not delivered
Labels: ready-for-agent · Confidence: certain (mechanism)
Evidence: comment promises same-key enqueue order (`internal/outbox/outbox.go:195-197`); failed publish backs off while later same-key rows pass (`:219-235`); same-tx rows share `created_at` and `sort.Slice` is unstable (`:198`). No ordering test exists.
Impact: order inversion at the broker on retry; consumers relying on per-key sequencing (wallet settlement, market projection) can process out of order.
Fix: monotonic claim key (BIGSERIAL or `(key, clock_timestamp(), id)`), claim ORDER BY that key, defer later same-key rows while an earlier one is in backoff; pin with the determinism test the checklist mandates.
Acceptance: a relay test that fails the first publish of a key, lets later same-key rows attempt publish, and asserts the broker received them in enqueue order — red on main, green after.

## High — wallet and custody

### ISSUE-6 — wallet: zero-amount ERC-20/TRC-20 Transfer permanently wedges a Coin's deposit watcher
Labels: ready-for-agent · Confidence: certain (code path)
Evidence: `internal/wallet/chain/evm/evm.go:228-244` and `internal/wallet/chain/tron/tron.go:154-166` build a Deposit with no positivity check; the insert violates `deposits CHECK (amount > 0)` (`migrations/wallet/0002_wallet.up.sql:103`); `Tick` errors before the cursor saves (`watcher.go:158-168`) so the same block re-scans forever (`watcher.go:405-412`). Impact: one cheap, address-targetable spam transaction halts credits for every Member of that Coin.
Fix: reject non-positive amounts in `parseTransferLog` and the TRC-20 branch before `RecordDetected`.
Acceptance: an adapter unit test feeding a 0-value Transfer log asserts it is skipped (not returned as a Deposit) — red on main, green after.

### ISSUE-7 — wallet: UTXO spend index is write-once; reconciliation audits it against itself
Labels: needs-triage (design choice between re-derive-on-rewind vs node-sourced) · Confidence: certain (code)
Evidence: `spendUtxo` only marks spent (`internal/wallet/watcher.go:295-301`); no un-mark path exists; `recordUtxo` never removes reorged ghosts (`:286-293`); for BTC/LTC the reconciliation "chain side" sums the same `utxos` table (`internal/wallet/run.go:216-229`), so `ReconcileCoin` compares the index with itself.
Impact: a reorg evicting a spending transaction permanently corrupts the index; reconciliation is structurally blind to it; `HotUtxos` under-counts and withdrawals fail "hot utxos < needed".
Fix (direction): on rewind, re-derive `utxos` from the re-scanned window; source the chain-side hot balance from the node (`scantxoutset`/daemon balance) rather than the audited table.
Acceptance: a watcher IT that simulates a reorg evicting a spending tx and asserts the index returns to the pre-spend state and reconciliation stays OK — red on main, green after.

### ISSUE-8 — wallet: signed-state crash recovery nulls the recorded txid and strands the withdrawal
Labels: ready-for-agent · Confidence: certain
Evidence: `internal/wallet/executor.go:109-118` — on failure the loop calls `MarkWithdrawalBroadcast(ctx, db, w.ID, "")` whose `NULLIF($4,'')` nulls the only record of a possibly-broadcast tx (`withdrawals.go:220-222`), then `failFrom(..., WSigned, ...)` targets `WHERE state='signed'` which the row no longer matches — no-op. `confirmTx` then answers "no txid to confirm" forever (`executor.go:238-239`). `GetCoin` error ignored (`:110`).
Impact: a crash in the recovery window destroys the chain-side record; the withdrawal is unconfirmable and unresolvable through the admin surface.
Fix: never null a recorded txid (append to an attempt-history column); resolve state transitions from the row's actual state.
Acceptance: an executor IT that drives the signed→crash→recovery path with a failing broadcast and asserts (a) the previously recorded txid survives and (b) the row reaches a resolvable state — red on main, green after.

### ISSUE-9 — wallet: evicted broadcast withdrawals/sweeps/hot-transfers have no reachable failed state
Labels: ready-for-agent · Confidence: certain
Evidence: `failEvicted` only files an incident (`executor.go:279-285`); `MarkWithdrawalFailed` is pinned `approved→failed` (`withdrawals.go:228-230`); refund and retry both require `failed` (`:193-195`, `:210-212`). Same shape for sweeps and hot transfers.
Impact: a Member stays debited after a chain-side eviction; only manual SQL resolves it.
Fix: allow `broadcast→failed` from the eviction path; route refund/retry through it.
Acceptance: an IT that evicts a broadcast withdrawal and asserts an admin retry (or refund) transitions the row — red on main (no reachable path), green after.

### ISSUE-10 — wallet/deploy: chain TLS verification fails open by default
Labels: ready-for-agent · Confidence: certain
Evidence: `internal/wallet/config.go:58` (`os.Getenv(...) != "false"` — unset means skip-verify); `deploy/docker-compose.yaml:224` hardcodes `MAL_CHAIN_TLS_SKIP_VERIFY: "true"` so the operator cannot disable it via `.env`.

Acceptance: a config unit test asserting the zero-value default is verify-on (red on main) plus `docker compose config` showing the value interpolated from the environment.

### ISSUE-11 — wallet: one poison event wedges all settlement; panics bypass the fatal log
Labels: ready-for-agent · Confidence: certain (path; trigger requires a malformed event)
Evidence: any `SettleEnvelope` error is fatal (`internal/wallet/consumer.go:41-71`); one bad `trade.fill` blocks every market in a permanent restart loop; `money.MustParse` panics on a well-formed-JSON/non-decimal amount (`settlement.go:31-35`) before the fatal-cause log (`run.go:70-73`) — the #51 checklist rule holds for errors but not panics. Same class as the exchange duplicate-ID crash loop (`apply.go:97-121`, `consumer.go:61-78`).
Impact: settlement availability hostage to any single malformed message; incident forensics lose the panic cause.
Fix: per-envelope attempts cap with a parked/dead-letter state; `recover()` in the consumer loop that logs and parks rather than dies; mirror the quarantine pass on the exchange side for duplicate order IDs (explicit rejection event instead of a crash loop).
Acceptance: an IT publishing a deliberately malformed `trade.fill` that asserts (a) subsequent well-formed Fills in the same topic still settle and (b) the poison is parked with an incident — red on main (consumer dies), green after.
